# 状态栏实时活动（灵动岛）设计

手机版在后台时，用一条持续更新的状态卡片告诉用户「有对话在跑、卡在等你、刚做完」。
本文记录状态集合、数据来源、图标策略、通知内容与后台保活，供后续维护对照。

## 一、目标与范围

- 用户在别的 App 里，也能看到还有没有对话在跑、是否卡在等他处理。
- 状态随进度更新，能一键回到 App。
- 多条对话合并成一条，不堆成一串通知；完成或失效后自动收起。
- 只做「由用户发起、进行中、有时效」的内容。一次性消息、普通提醒走普通推送，不进状态栏。

## 二、设计原则

1. **一条卡片**：全部状态共用同一条通知（固定 ID），状态变化只改写它，不新增。`setOnlyAlertOnce` 避免重复提示。
2. **图标统一**：全程用同一个应用 logo（IP 形象），状态变化只改文字/数字，不做图标轮换、不做动画图标。理由见第三节。
3. **优先级**：待处理（待批准/待回答）> 运行中 > 已完成。同一时刻只显示最高优先级那一条，其余合并计数。
4. **不堆叠**：多个对话按数量合并，显示「N 个运行中 / N 个待处理」。
5. **自动收起**：完成类停留几分钟后自动撤；用户回到 App 或关掉开关也立即撤。
6. **保活必须有意义**：前台服务只在有会话正在跑（需要实时进度、需要连接不断）时启用，跑完/空闲立即停。**绝不闲置常驻**——开发者图省事让服务一直挂着，是偷懒、不合理的行为。`START_NOT_STICKY` 不自启，不申请忽略电池优化，不注册开机广播。详见第七节。
7. **降级**：拿不到系统常驻状态位（Live Update / 焦点授权）时，退化成普通常驻通知。不做悬浮窗叠加。

## 三、图标与形象

状态栏的小图标由系统染成纯白，只剩剪影；灵动岛/超级岛同样空间极小。**频繁换图标用户记不住，只会迷茫**。因此：

- 全程固定用应用 logo，作为可识别的 IP 形象。
- HyperOS 超级岛：`miui.focus.pic_icon` 用 `R.mipmap.app_icon`（彩色大图）。
- 普通通知：`setSmallIcon` 只能是单色占位（系统染色），应用彩色图标走 `setLargeIcon(R.drawable.baocodex_logo)`。
- 不跟随「思考中/执行中」等状态换图，不做帧动画图标。

## 四、可对接的数据源

电脑端协议里，会话级状态只有三种：

```dart
enum LinkSessionStatus { running, needsInput, idle }
```

更细的信号只在**已订阅（打开过）的会话**里可见（`LinkSessionUpdate`）：

| 信号 | 取值 | 能判什么 |
| --- | --- | --- |
| `live` | bool | 这一回合在跑 |
| `interaction['t']` | `approval` / `question` / 其他 | 待批准 / 待回答 |
| `tasks[]` | `kind` / `status` / `description` / `startedAt` | 后台任务数、是否失败、任务开始时间 |
| `changes` | `{path, added, removed}` | 未保留改动数 |
| `context` | `{window, used, ...}` | 上下文占用（可算百分比） |
| `goal['state']` | `active` / `met` / `stopped` / `failed` | 目标状态 |
| `items[]` 的 `LiveStatusItem` | 桌面英文活动标签 | 当前在做什么（规划/压缩等） |

> 失败只能到**任务级**（某个后台任务 failed）或回合内行级（最后一条命令/工具 failed）。会话级 `status` 不区分「失败」和「正常结束」，所以不推断整个会话失败，也不单独设「出错了」状态。
>
> 「已取消」在桌面端只表现为 `live=false`，与正常结束同形，无法可靠区分，不单独设状态。
>
> 细分（待批准 / 待回答、上下文用量）只在**已订阅（打开过）的会话**里拿得到；其余会话只有 `needsInput`，用统称「待处理」兜底。

## 五、状态定义

这里有两层，不是二选一：**能细分就细分，细分不了用统称。**

| 状态 | 触发条件 | 数据来源 | 优先级 |
| --- | --- | --- | --- |
| **待批准** | 等批准（含等开始计划） | `needsInput` + `interaction.t=='approval'` | 最高 |
| **待回答** | 等回答 | `needsInput` + `interaction.t=='question'` | 最高 |
| **待处理** | 等你处理，但判不出具体类型 | `needsInput`（无 buffer 或多条） | 最高 |
| **运行中** | 回合在跑 | `status==running` | 中 |
| **已完成** | 回合结束且未看 | `status==idle && unread`（仅后台） | 低 |

- 单个会话能判出 `interaction.t` 时用「待批准 / 待回答」；判不出、或多条合并时用统称「待处理」。
- 不做「思考中 / 执行中 / 生成中」的进一步细分：拿不到可靠、稳定的信号，且细分意义不大。
- **细分只改文字，不改图标**（图标始终是应用 logo，见第三节）。

## 六、通知内容

保持两行结构：**第一行状态词，第二行对话标题或聚合信息**。不展开明细——它只是通知，用户点进去回到 App 再操作才合理。

| 内容 | 来源 | 说明 |
| --- | --- | --- |
| 状态词 | 见第五节 | 待批准 / 待回答 / 待处理 / 运行中 / 已完成 |
| 上下文用量 | `LinkSessionUpdate.context`（`used / window`） | **仅当前会话可得**，追加在第一行如「运行中 · 上下文 45%」；85% 这类数字本身即可读懂，不加「偏高」等注解 |
| 对话标题 | `SessionSummary.title` | 第二行；多条时改为聚合计数 |
| 聚合计数 | 在线会话按状态聚合 | 「2 个运行中」「2 个待处理」 |

示例：

```
运行中 · 上下文 45%
修复登录页的滚动 bug
```

```
待批准
修复登录页的滚动 bug
```

```
待处理
2 个待处理
```

```
运行中
2 个运行中
```

```
已完成
修复登录页的滚动 bug
```

**操作按钮**：

- **停止**：运行中时通知带一个「停止」按钮，直接停掉那一轮，不必打开 App。属通知交互，不是额外弹窗。进程被系统回收时该按钮无效（连接也没了），属可接受的降级。
- 点击通知正文 = 打开 App 到对应会话。

**不做**：

- **进度条**（含不确定进度条）：无意义，不做。1.0.8 里 `setProgress` 仅 Android <16 生效，一并删除。
- **展开明细（`BigTextStyle`）**：多一步操作没必要，通知只负责让人看到、点进去。
- **已用时长**：`SessionSummary` 无开始时间，需本地记录，当前版本不做。
- **多图标/动画**：见第三节，不做。
- **悬浮胶囊**：需 `SYSTEM_ALERT_WINDOW`，违背最小权限的约束，不做。

## 七、后台保活与「消失」根因

### 消失的原因

切后台后若不加前台服务，灵动岛约 20~30 秒消失。原因链：

1. 切后台 → Flutter 进程被系统（HyperOS）冻结；
2. QUIC keep-alive（5 秒）停止；
3. 连接 `idle_timeout` 为 20 秒（`vendor/bao_iroh/rust/src/lib.rs`），超时拆链路；
4. 链路断开 → 电脑判离线 → `_syncLiveActivity()` 过滤掉全部会话 → `reduce()` 返回 null → 撤通知。

注意：Android 通知本身不依赖进程存活，进程被杀它也会留在状态栏。所以「消失」不是系统撤的，而是链路断开后我们主动 `clear()` 的结果。

### 方案：极简前台服务

为了让连接在后台不断、灵动岛有真实进度，用一个极简前台服务 `LiveService` 顶住进程：

- **只在有会话正在跑时保活**；完成态、空闲，或只有「待处理」（状态本身稳定、不必耗电）时都不占服务。判据是「有没有会话在跑」，与此刻显示哪一条无关——哪怕界面显示的是待处理，只要别处有在跑的，也要保活。
- **复用同一条通知**（同一个 ID `9003`），不另起一条；用户始终只看到一条。完成态把通知脱离前台持有（`STOP_FOREGROUND_DETACH`）后服务自停，通知靠自身超时收起。
- `START_NOT_STICKY`：被系统回收或用户强行停止后**不自启**，需重新打开 App。
- **不申请** `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`（忽略电池优化），不注册开机广播。
- 需要普通权限 `FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_REMOTE_MESSAGING`（安装即给，无需用户授权）。
- 系统拒绝进前台时静默降级为普通通知，不崩溃。

开关联动：设置里的「状态栏实时活动（灵动岛）」关掉后，Dart 不再下发 running，服务随之停止——**关掉灵动岛就等于关掉保活**。

### 降级

- 前台服务被系统拒绝或进程被杀：通知仍在（普通通知），数据变为冻结，回前台 `resume()` 后自动重连刷新。
- 是否被冻结可用 `adb logcat` 连真机确认（属调试既有产物范围）。

## 八、降级与生命周期

- **系统能力探测**：Android 16 Live Update（`android.requestPromotedOngoing`）拿不到 → 退普通常驻通知。
- **HyperOS 超级岛**：需 SystemUI 焦点授权（`canShowFocus`），拿不到就跳过模板，仍是普通通知。
- **开关实时生效**：设置页开关变化后立即重算并刷新，无需重启。
- **收起时机**：用户回到 App、关掉开关、对话全部结束、或进程结束。
- **保活生命周期**：只在有会话正在跑时保持前台服务；跑完即 detach（通知短暂停留后超时收起），空闲不占服务。

## 九、边界规则

- 只在「待处理 / 运行中 / 刚完成未看」时出现；空闲、离线、无任务时不显示。
- 内容只放状态词与数量，不放对话正文、代码、命令。
- 已完成态仅在**后台**出现；用户正看着该对话时不算未读、不提示。

## 十、实现落点

| 文件 | 职责 |
| --- | --- |
| `lib/state/live_activity.dart` | `reduce()` 决定显示哪一条；调用原生通道；监听通知上的「停止」 |
| `lib/state/app_state.dart` | `_syncLiveActivity()` 收集在线会话（含 buffer 细分），去重后下发；处理「停止」回调 |
| `android/.../LiveActivity.kt` | 发通知、请求 promoted ongoing、拼 HyperOS 焦点模板、加「停止」按钮 |
| `android/.../LiveService.kt` | 极简前台服务，顶住进程；复用同一条通知，空闲即停 |
| `android/.../LiveStopReceiver.kt` | 接收「停止」广播，把动作推回 Dart |
| `android/.../PlatformBridge.kt` | `local.baocode.mobile/live` 的 `update` / `clear`；`live_actions` 事件流 |

细分（待批准 / 待回答、上下文用量）在 `reduce()` 内完成：有 buffer 就细化，没有就用统称「待处理」。不新增状态机，不解析命令文本。图标始终统一，仅文字/数字变化。
